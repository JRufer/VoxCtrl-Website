GETTING STARTED / SERVER

VoxCtrl server

voxctrl-server runs VoxCtrl's speech models on one machine so the app on another doesn't have to. The app keeps everything that needs your desktop (hotkeys, the microphone, the overlay, typing the result) and sends the audio to the server to be transcribed. The server can also run dictation cleanup and text-to-speech for its clients, and pass their AI processing on to a language model.

Use it when a laptop is short on RAM, battery or GPU and a desktop or home server has plenty, when several computers should share one model instead of each loading its own, or when you want a large model without dedicating part of your workstation to it. The server has no window, no tray icon and no audio device: it is one program listening on a network port, 8787 by default.

What runs where

What Where it runs
Hotkeys, microphone, overlay, typing the text Client (the VoxCtrl app)
Speech recognition (whisper.cpp, Moonshine, Parakeet) Server
Filler removal, spoken punctuation, snippets, custom vocabulary Client
S1-mini dictation cleanup Server, when turned on at both ends; otherwise client
AI processing (the OpenAI-compatible LLM step) Through the server to the service it is pointed at, when turned on at both ends; otherwise wherever the client's own OpenAI API settings point
Text-to-speech Server, when turned on there and the client's TTS engine is VoxCtrl server; otherwise client. The audio always plays on the client

Cleanup, text-to-speech and AI processing are each off until you turn them on at both ends, so a client keeps using its own until then.

Choose a way to run it

How Best for
From the VoxCtrl AppImage (--server) A desktop or laptop that has, or can have, the VoxCtrl app. Nothing to build
Arch Linux: voxctrl-server from the AUR A headless Arch machine. Installs a system service, no desktop dependencies
Docker A home server or NAS that already runs containers
A system service built from source A headless machine on another distribution, without Docker

The server needs Linux on x86-64, enough memory for the model you pick, and internet access the first time it starts, to download that model. Give it a fixed address on your network (reserve its IP in your router, or use its hostname) so clients keep finding it.

From the AppImage

The VoxCtrl AppImage is also the server (from 0.9.17). Started with --server it runs the same server, with no window, tray icon or microphone:

chmod +x VoxCtrl-linux-x86_64-vulkan.AppImage
./VoxCtrl-linux-x86_64-vulkan.AppImage --server

The first start downloads the model, then prints the address, the API key and a pairing code. Stop it with Ctrl+C. To see the code again later:

./VoxCtrl-linux-x86_64-vulkan.AppImage --server --pairing-code

Everything after --server is a server option: --server --help, --server --print-config, --server --bind 0.0.0.0:9000. The .deb works the same way: voxctrl --server. Settings go in ~/.config/voxctrl/server.toml, which the first start creates, or in environment variables:

VOXCTRL_SERVER_BACKEND=whisper-cpp VOXCTRL_SERVER_MODEL=large-v3-turbo \
  ./VoxCtrl-linux-x86_64-vulkan.AppImage --server

The server keeps its own settings file but uses the app's model folder, so a model the app already downloaded is not downloaded again, and the GPU build gives the server the same acceleration as the app. App and server can run on one machine at once; each loads its own copy of its model.

ⓘ In server mode the AppImage still loads the desktop libraries it needs as an app (GTK, GLib, GStreamer, Wayland and OpenGL client libraries). Any desktop install has them, and it runs fine over SSH with nobody logged in. A minimal server install usually doesn't, and the AppImage stops with error while loading shared libraries: use the AUR package or Docker there.

To start it with the machine, run it as a systemd user service. The unit file is in the repository as packaging/systemd/voxctrl-server-appimage.service; with the AppImage in ~/Applications/:

systemctl --user daemon-reload
systemctl --user enable --now voxctrl-server
sudo loginctl enable-linger "$USER"     # keep it running when you are logged out

The app's built-in updater updates the file it was started from, so an AppImage used for both the app and the server is updated by the app; restart the service afterwards.

Arch Linux: the AUR

On Arch and Arch-based systems, voxctrl-server (from 0.9.18) builds the server and installs the systemd service, the voxctrl service user and /var/lib/voxctrl, where settings and models are kept:

paru -S voxctrl-server        # or: yay -S voxctrl-server
sudo systemctl enable --now voxctrl-server
sudo journalctl -u voxctrl-server -f      # first start: model download, then the API key
sudo -u voxctrl -H voxctrl-server --pairing-code

It is built from source on your machine, which takes a while (it compiles whisper.cpp and llama.cpp). It has no desktop dependencies and can be installed next to the voxctrl app packages. whisper.cpp and dictation cleanup use a GPU when a Vulkan driver is installed, and the CPU otherwise. The settings file is /var/lib/voxctrl/.config/voxctrl/server.toml; after an upgrade, sudo systemctl restart voxctrl-server.

Docker

There is no published image yet, so the image is built from source on your machine. That can take from several minutes to half an hour, and only happens on the first start and after an upgrade.

git clone https://github.com/JRufer/VoxCtrl.git
cd VoxCtrl/packaging/docker
cp .env.example .env      # pick the engine, model and port here
docker compose up -d --build
docker compose logs -f    # first start: model download, then the API key

The Docker setup defaults to parakeet / tdt-0.6b-v3. Everything the server writes lives in the voxctrl-data volume, which survives docker compose down and upgrades. To print the pairing code: docker exec voxctrl-server voxctrl-server --pairing-code. A container can't tell what address it is reached by, so either type the server's address into the app before pasting the code, or set VOXCTRL_SERVER_PUBLIC_HOST so the code carries it.

A system service on other distributions

There is no prebuilt server binary in the releases yet, so this builds from source with Rust, CMake and Clang, then installs the binary and the unit file from packaging/systemd/. The steps, with the build tools for Debian, Arch and Fedora, are in the server guide.

Choose a model

The server runs one model at a time, with the same engines and model names as the app. Started with no settings at all it uses whisper-cpp with tiny: enough to check everything works, not what you want to dictate with.

Engine (backend) Models Approx. memory Notes
parakeet tdt-0.6b-v3, tdt-0.6b-v3-int8, tdt-0.6b-v3-redux, phonon-2 ~665 MB (redux ~420 MB) Fast on a CPU; no GPU needed. A good default for a server
whisper-cpp tiny to large-v3, large-v3-turbo, and English-only .en variants 75 MB to 3.1 GB Widest language coverage. medium and larger are slow without a GPU
moonshine tiny, base ~240–530 MB Small and fast on a CPU. English

Connect the app

On each computer that should use the server:

  • Open Settings → Engine and set Backend to Remote Speech Engine.
  • Paste the server's pairing code (it starts with vxpair_ and holds the API key, so treat it like one) and click Pair. The endpoint, the API key and, with encryption on, the server's certificate are filled in and the connection is tested.
  • Or set it up by hand: type just the machine's name or IP (192.168.1.50 becomes http://192.168.1.50:8787/v1), enter the API key, and click Test Connection, which says what the server offers. This doesn't work with encryption on.
  • In the same section, choose a Fallback engine and whether to Run dictation cleanup on the server, Use the server for AI processing and Use the server for text-to-speech.

Live text in the overlay works over the server too (VoxCtrl 0.9.2 or newer on the client): the app sends short clips of what you have said so far a few times a second. Vocabulary and snippets still work; the client sends your vocabulary as a hint and applies snippets, punctuation and cleanup to the result itself.

When the server can't be reached

With a Fallback engine set (Whisper.cpp, Moonshine or Parakeet), the dictation you just made is transcribed on your computer instead, so nothing you said is lost. The fallback model isn't loaded while the server is reachable. The tray icon shows an amber badge with a slash, one notification says the fallback is in use, and every overlay shows a small OFFLINE mark. The app checks the server every 15 seconds and goes back to it as soon as it answers. With the fallback set to None, each dictation fails with an error until the server is back.

Free the disk space your local models used

Settings → Engine → Downloaded Models → Clean up models… first asks which fallback engine to keep, then lists the speech, cleanup and voice models that are no longer in use, with their sizes, and removes the ones you confirm. Custom voices are never removed, and a removed model can be downloaded again by selecting it.

What else the server can do

Dictation cleanup

S1-mini cleanup can run on the server, so a client loads no language model at all. Turn it on with VOXCTRL_SERVER_CLEANUP=true (Docker) or [cleanup] enabled = true in server.toml, restart, then turn on Run dictation cleanup on the server in the app. The server downloads the model (about 470 MB) on that start. Needs 0.9.5 or newer at both ends.

Text-to-speech

The server synthesizes and the client plays the audio. You decide on the server which engines exist (VOXCTRL_SERVER_TTS=true and VOXCTRL_SERVER_TTS_ENGINES=kitten_tts_2,piper, or [tts] and [speech] in server.toml); each client then picks an engine and a voice under Settings → TTS. Voices you clone in the app are uploaded to the server, kept for your computer only, and removed from the server when you delete them in the app. Nothing a client sends makes the server download anything. Needs 0.9.11 or newer at both ends.

AI processing

AI processing (a hotkey sending what you dictated to a language model to be rewritten) can go through the server to one OpenAI-compatible service you set up there, such as Ollama or llama.cpp on the server machine, or a hosted provider whose key you'd rather keep off every laptop. The model doesn't run inside voxctrl-server; it passes requests on.

# server.toml
[llm]
enabled = true
endpoint = "http://localhost:11434"
model = "llama3.2:1b"

Or in Docker, VOXCTRL_SERVER_LLM=true, VOXCTRL_SERVER_LLM_ENDPOINT and VOXCTRL_SERVER_LLM_MODEL (use http://host.docker.internal:11434 for a service on the same machine). Then turn on Use the VoxCtrl server under Settings → OpenAI API, or Use the server for AI processing under Settings → Engine; Check the server shows the model it answers with. Your prompts and which hotkeys use AI processing stay yours; the model is the server's. If the request fails for any reason, the text is typed as you dictated it. Needs 0.9.16 or newer at both ends.

Security

  • Keep the API key on. Every request must carry it.
  • By default the connection is plain HTTP, so audio and the key cross the network in the clear. On your own LAN that is usually acceptable; anywhere else, turn on encryption.
  • Encryption: VOXCTRL_SERVER_TLS=true or [tls] enabled = true. The server makes its own certificate, the pairing code carries its fingerprint, and a paired app accepts that one certificate and never falls back to plain HTTP. Clients set up before have to be paired again. Needs 0.9.15 or newer at both ends.
  • Don't forward the port from the internet, with or without encryption. For access from outside, use a VPN such as WireGuard or Tailscale, or a reverse proxy that adds HTTPS.
  • The server keeps neither your audio nor your text. Audio is held in memory for one request, and the log records lengths and timings, never what was said.
