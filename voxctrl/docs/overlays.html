AI & VOICE / OVERLAYS

Overlays

voxctrl displays a transparent always-on-top HUD while recording, while TTS is speaking, or while the MCP server is actively recording. Eight built-in styles are rendered by an ordinary Tauri WebviewWindow — the same component tree used for the style preview in Settings, so what you see there is exactly what appears during a real dictation. Switch between them, or add a style of your own, in Settings → Visual Feedback.

Built-in styles

The default is Ocean Wave. All styles share three state palettes: Recording (the style's signature color), Initializing (amber), and Processing (sky blue).

Style config value Description
Ocean Wave (default) blue_wave A glass tide pool at night with a glowing moon and rising bubbles. Three layered sine waves (deep blue → cyan → ice teal) whose tide level and amplitude rise with your voice; a buoy tag floats on the front wave showing the active target.
Voice Card voice_card A membership card with a gold contact chip, embossed branding, and a holographic sheen. A 20×6 VU-meter LED dot matrix (green → amber → red) with real VU ballistics; the card flips in and out on load/unload.
Waveform waveform A green-phosphor oscilloscope ("WAVEFORM // OSC-01") with a graticule grid and a live scrolling line trace of the microphone signal. Powers on/off like a CRT.
Pulse Ring pulse A sonar/radar dial with a rotating sweep arm, expanding pulse rings, contact blips, and an audio-reactive core, paired with a "PULSE // TARGET LOCK" plate.
Mono Bars mono_bars A hyper-minimal black & white panel — no color, no gradients. A 5-bar level meter, centre-weighted, with a gentle ripple while recording.
Neon Spectrum spectrum A 16-band equalizer in a deep-violet panel with a magenta-to-cyan gradient. Bass bands swing wider and slower; treble bands flicker faster.
Retro Terminal terminal A DOS-blue console window with a three-dot title bar and a block-character ASCII meter (█/·) that fills left-to-right with the audio level.
Analog VU vinyl A warm, vintage VU meter in cream and amber tones with a spring-loaded needle that sweeps a -20 to +3 scale with realistic ballistics.

To disable the overlay entirely, set ui.overlay_style = "none" in ~/.config/voxctrl/config.json or toggle it off in Settings → Visual Feedback.

Selecting a style

Open Settings → Visual Feedback → Overlay style dropdown. Changes take effect immediately and are hot-switched without recreating the window. The setting is written to config.json as ui.overlay_style.

// config.json excerpt
{
  "ui": {
    "show_overlay": true,
    "overlay_style": "blue_wave",
    "overlay_position": "center",
    "overlay_monitor": "primary"
  }
}

Valid overlay_style values: "blue_wave", "voice_card", "waveform", "pulse", "mono_bars", "spectrum", "terminal", "vinyl", "none" — or the name of any custom overlay folder you've added.

Positioning

The overlay window can be positioned dynamically on the active monitor via Settings → Visual & Feedback → Overlay position, or via ui.overlay_position in config.json:

  • "center" (default) — exact horizontal and vertical center of the active monitor
  • "top" — horizontal center, 60 logical pixels from the top
  • "bottom" — horizontal center, 60 logical pixels from the bottom

Positions are calculated in physical pixels relative to the display's current scale factor, so placement is resolution-independent on 1080p, 1440p, and 4K monitors. Changes apply instantly if the overlay is currently visible.

Multi-monitor targeting

In multi-monitor setups, you can pin the overlay to a specific display via Settings → Visual & Feedback → Overlay display, or ui.overlay_monitor:

  • "primary" (default) — constrains the overlay to the OS-defined primary display
  • Specific monitor name (e.g. "HDMI-1", "DP-2") — connected displays are queried once at startup; selecting one binds the overlay to that panel

If the configured target monitor is unplugged or disconnected at runtime, VoxCtrl automatically fails over to the primary monitor and shows a golden warning badge in the settings UI to flag that fallback mode is active.

Routing indicator badge

Every overlay shows a small label with the active target's human-readable name (e.g. "Focused Window", "Hermes Agent", "Voice Journal"). When you use multiple hotkeys to route to different destinations, the badge changes with each activation. The label comes from the label field on the active target definition in targets.toml.

Speaking pill

While TTS is responding, a green "SYSTEM RESPONDING" pill slides up from the bottom of the overlay with a live mini-equalizer and the active target label, and slides back down when speech ends.

How it works

The overlay — built-in or custom — is rendered by an ordinary Tauri WebviewWindow: a borderless, transparent, always-on-top, click-through window (592×222 logical px) drawn over whatever application is in focus. It's the same component tree used for the style preview in Settings, so what you see there is exactly what appears during a real dictation. State reaches it the same way it reaches every other window in the app — the status-tick and audio-level Tauri events the backend already emits app-wide — so there's no separate IPC protocol just for the overlay.

The window is built once at startup and kept for the whole session, rendering nothing while idle — not rebuilt on every dictation. An interim v0.5.9 build had switched to creating it fresh per activation as a workaround for a stale-frame bug (see below); v0.6.1 fixes the actual cause and reverts to the built-once approach, so there's no longer a brief black-box flash before each overlay appears.

The v0.6.1 fix: released AppImages bundle their own copy of WebKitGTK, and the version bundled by the build host rendered a transparent window's compositing layers without their alpha channel — static content drew fine, but anything mid-animation turned into an opaque copy of its last frame, which is what caused the closing animation's blurry smear (and, before that, made a hidden-then-reshown window keep displaying whatever was last composited). VoxCtrl now prefers the WebKitGTK already installed on your system, falling back to its bundled copy only when none is found — every newer WebKitGTK renders the overlay correctly, which is most desktops and all rolling releases. This is owned entirely by the Rust backend, so it works the same regardless of which style — built-in or custom — is selected.

The window is fully transparent except for drawn pixels, stays always-on-top (re-asserted on a roughly 1-second heartbeat while a dictation is active, since a window manager can restack it mid-session and it never recovers on its own), and is click-through (cursor hit-testing disabled at the windowing-system level), so mouse events pass cleanly through to the window beneath it. On Wayland, VoxCtrl forces the whole app onto XWayland at startup to get real positioning and always-on-top back, since Wayland gives clients no way to do either themselves.

Every built-in style plays a dedicated spring-driven load animation when it appears and an unload animation when it disappears, driven client-side in Svelte — the window stays alive for the whole animation, so the unload animation is never cut off mid-play.

The overlay is shown automatically when recording starts and hidden when transcription completes, provided ui.show_overlay = true.

Custom overlay styles

New in v0.5.7. Beyond the eight built-in styles, VoxCtrl loads user-authored styles from an overlays folder — ~/.local/share/voxctrl/overlays on Linux, the platform-equivalent path elsewhere. Every subfolder containing an index.html and a style.css becomes a selectable style in Settings → Visual Feedback → Overlay style, named after the folder. New or renamed folders show up the next time that dropdown opens, and both files are read fresh, together, every time you select that style — including re-selecting the one already active — and again every time the overlay next activates. No app restart needed either way.

VoxCtrl seeds a Custom/ folder the first time it runs: a complete, working example — a copy of the built-in Voice Card style with one line changed (VOXCTRL → CUSTOM OVERLAY) — so you can compare the two and see exactly what a real overlay folder looks like. VoxCtrl makes sure Custom/ exists and never touches it again once it does, edited or not, so it's safe to experiment in directly. To keep your own style alongside it, duplicate Custom/, rename the copy (the folder name becomes the style's name in Settings), and edit its two files.

There's no <script> tag. The overlay window's content-security-policy is script-src 'self' with no unsafe-inline, which silently blocks inline <script> execution everywhere in the app, custom overlays included, with no visible error (there's no console in that window). Drive your overlay from CSS instead: VoxCtrl continuously writes live state onto custom properties on the page root, for var()/calc() to read directly — no script needed.

Custom propertyRangeMeaning
--voxctrl-recording0 / 1Microphone is capturing
--voxctrl-processing0 / 1Audio is being transcribed
--voxctrl-speaking0 / 1TTS is playing a reply
--voxctrl-mcp-recording0 / 1The MCP server is actively recording
--voxctrl-audio-ready0 / 1The audio pipeline has warmed up
--voxctrl-audio-level0..1Smoothed microphone level

CSS can't swap text content based on a variable, so for anything that needs to change text — not just color — the trick Custom/ uses is to pre-render every possible label stacked on top of each other and toggle each one's opacity with the boolean-algebra formula that should show it. A custom overlay's index.html also gets one-time {{target}} / {{trigger}} placeholder substitution for the active routing target's label. See the shipped Custom/index.html and style.css for a fully commented, working example of both techniques.

Looking for a starting point instead of the blank-page version? The VoxCtrl-Scripts-and-Overlays repository collects community-made overlay styles — ready to drop straight into the folder — alongside scripts you can trigger with a voice command.
